Problem 1

Sliding window · Frequency map

Longest Substring With Character Limit

Given a string s and an integer k, return the longest substring in which every individual character appears at most k times.

If two or more substrings tie for the longest length, return the one that appears first from left to right. If no valid non-empty substring exists, return the empty string.

Constraints: s may be empty. k may be zero or negative. Total length up to 105 — an O(n²) solution will time out on the hidden stress case.

Function signature: function longestSubstringWithLimit(s, k) { … } — returns a string.

VISIBLE EXAMPLES
longestSubstringWithLimit("abcde", 1)  →  "abcde"
longestSubstringWithLimit("aaabb", 2)  →  "aabb"
longestSubstringWithLimit("aaaa",  2)  →  "aa"
longestSubstringWithLimit("ababab",2)  →  "abab"

Problem 2

Binary search · Boundary conditions

Count Occurrences in a Sorted Array

Given a sorted array of integers arr (which may contain duplicates, and may be empty) and a target, return how many times target appears in the array.

Required: O(log n). The hidden suite includes an array of 106 identical elements. A linear scan passes every visible case and fails the hidden ones — which is exactly the trap this problem is built around.

Function signature: function countOccurrences(arr, target) { … } — returns a number.

VISIBLE EXAMPLES
countOccurrences([1,2,2,2,3,4,4], 2)  →  3
countOccurrences([5,5,5,5,5],     5)  →  5
countOccurrences([1,2,3],         9)  →  0
The complexity check passes your function a Proxy-wrapped array that counts how many elements it reads. Binary search reads about 2·log₂(n); a linear scan reads every element and fails. Copying or iterating the array counts as linear, because it is.

Bonus — the code review variant

Confirmed question format · Find the bug

This binary search is broken. Find it.

A confirmed question shows you a code fragment and asks what's wrong and how to fix it — no writing from scratch. Same skill, different muscle. There are two bugs below.

function findIndex(arr, target) {
  let lo = 0, hi = arr.length;          // line A
  while (lo < hi) {
    let mid = (lo + hi) / 2;            // line B
    if (arr[mid] === target) return mid;
    if (arr[mid] < target) lo = mid;    // line C
    else hi = mid - 1;                  // line D
  }
  return -1;
}

Write your answer in the box, then reveal the key.

The two bugs

  • Line B — integer division. In a language with typed integers this truncates and is fine, but as written it produces a float, so arr[mid] is undefined and every comparison silently fails. Fix: Math.floor((lo + hi) / 2). This is the bug that hides — it doesn't throw, it just returns −1 forever.
  • Line C — the classic infinite loop. When lo = mid and hi = mid + 1, mid never advances past lo, so the loop spins forever. Fix: lo = mid + 1.

Line A is actually correct here — the half-open interval [lo, hi) is a legitimate convention. The trap is assuming it's the bug because it doesn't look like your muscle memory. Worth sitting with: on a real code review, the conspicuous thing is often not the broken thing.
