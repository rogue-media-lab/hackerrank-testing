The test, precisely

What's actually in front of you, from candidates who took this exact assessment in 2026.

  • 90 minutes, 2 coding problems, no multiple choice. That's the dominant 2026 format. A less common variant runs 60 minutes with 7 MCQs plus 2 problems.
  • Difficulty: LeetCode Easy to Medium, occasionally one Hard served first.
  • Language is your choice — Python, Java, JavaScript, Ruby all available. Use the one you're fastest in under a clock. It is not scored on language.
  • Scored on test-case pass rate, and hidden cases count exactly the same as the visible ones. Run button turns samples green and tells you nothing about your score.
  • Copy-paste is tracked. No webcam, no screen recording. Avoid pasting large blocks.
  • Estimated pass rate is about 30%, and a failure triggers a 6-month cooldown. This is a one-shot — prep properly and take it once.

Focus — the whole list

Six patterns. That's the confirmed question pool across every report. Nothing exotic.

  1. Arrays and strings — highest frequency, present in every single report.
  2. Hash maps — frequency counting, lookup optimization.
  3. Two-pointer — sorted traversal, pair finding, in-place partitioning.
  4. Sliding window — fixed and variable width. One candidate's actual second question was this.
  5. Binary search — including debugging someone else's broken binary search. Appeared twice.
  6. BFS — single and multi-source. Not general graph theory; just the grid-flooding kind.

Skip these entirely

Dynamic programming. Graph algorithms beyond BFS. System design. Trie. Union-find. Backtracking. None of these appear anywhere in the confirmed question pool. Every hour spent on them is an hour stolen from sliding window. If you're short on time, this is where you buy it back.

Pre-flight — do this on the machine you'll test on

Straight from HackerRank's own candidate FAQ. These are the failures that have nothing to do with your coding.

  • Wired or solid Wi-Fi, and power plugged in. The timer keeps running if your connection drops, and there is no retake. Submitted work auto-saves, so a dropout isn't fatal — but the clock never stops.

Where people actually fail

The dominant failure is not hard problems. It's passing all visible cases and failing hidden ones — and it happens on easy problems, not hard ones.

Run this list before every submit

empty inputEmpty string, empty array, null. Does it crash or return something sane?
single elementArray of length 1. Loops that assume a pair or a neighbor will break here.
no valid answerThe case where nothing satisfies the condition. What do you return — 0, −1, empty?
everything validAll elements qualify. Does your window logic still terminate correctly?
boundary valuesZeros, negatives, duplicates, maximum constraint sizes.
complexityRead the constraints. If n is 105, an O(n²) solution times out on hidden stress tests even though it's correct.

Strategy under the clock

  • Read both problems first. Thirty seconds. If one is clearly easier, bank it and move — a solved easy problem is points you keep.
  • Correct beats clever. Scoring is by test cases passed. A brute force that passes everything outscores an elegant solution that trips on one boundary. Get it working, then improve if time allows.
  • Don't burn twenty minutes on one edge case. Set a hard ceiling — if you're stuck more than ten minutes on a single input, move to the other problem and come back.
  • Write the naive version first. Then optimize. You can't lose points for having working code.
